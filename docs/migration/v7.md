# Migrating to v7

Atlas 7 keeps the v6 storage format. Outlook, OneDrive, and SharePoint backups written by v6 stay readable, incremental runs continue where they left off, and no fresh backup is needed. What changes is how the CLI holds Microsoft Entra credentials, and that is the only step most installations need.

```bash
npm install -g @wisecom/atlas-cli@7
atlas tenants list         # existing credentials appear as the "default" profile
atlas tenants validate     # Graph token check for the selected profile
atlas config validate      # S3 check
```

## What changed

| Area                    | v6                                                                  | v7                                                                                                                                        |
| ----------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Entra credentials (CLI) | One set, `atlas config set tenant.id`, `client.id`, `client.secret` | Named [tenant profiles](/configuration#tenant-profiles), managed with `atlas tenants`. Existing credentials load as the `default` profile |
| `atlas config`          | Every key, `validate` checks Graph and S3                           | Shared S3 and passphrase keys only, `validate` checks S3                                                                                  |
| Selecting a tenant      | Swap `ATLAS_TENANT_ID`, `ATLAS_CLIENT_ID`, `ATLAS_CLIENT_SECRET`    | `--profile <name>`, `ATLAS_PROFILE`, or `atlas tenants use`                                                                               |
| Cross-tenant restore    | Manual credential swap                                              | `--target-profile` on the CLI, `createTenant` and `targetTenant` in the SDK                                                               |
| Workloads               | Outlook, OneDrive, SharePoint                                       | Adds [Contacts](/contacts-backup), [Calendar](/calendar-backup), and [Teams](/teams-backup) channel messages                              |
| Storage format          | v6 keys                                                             | Unchanged. Contacts, Calendar, and Teams add the `contacts/`, `calendar/`, and `teams/` prefixes                                          |

## CLI credentials move into tenant profiles

A tenant profile is one app registration: tenant ID, client ID, and client secret. S3 settings and the encryption passphrase stay shared across profiles. See [Configuration](/configuration#tenant-profiles) for the stored layout and selection order.

### What keeps working

- **The encrypted store.** Top-level `tenant_id`, `client_id`, and `client_secret` from v6 load as the `default` profile. The first `atlas tenants` write moves them into `tenants.default` in the store.
- **`atlas.config.json`.** Top-level Graph fields in the file are read as `default` too. Atlas never rewrites the file.
- **`ATLAS_*` environment variables.** `ATLAS_TENANT_ID`, `ATLAS_CLIENT_ID`, and `ATLAS_CLIENT_SECRET` still work and override the selected profile. A CI job or container that sets all three and stores no profile runs unchanged, with no new output.
- **`-t, --tenant`.** It still overrides the tenant whose bucket a command reads. Without it, the selected profile's tenant ID names the bucket, `atlas-<tenant-id>`.

### What breaks

Scripts that manage the Graph credentials through `atlas config` fail with a message that points to `atlas tenants add`. Replace them as follows:

| v6                                                | v7                                                                                       |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `atlas config set tenant.id <id>`                 | `atlas tenants add <name> --tenant-id <id> --client-id <id> --client-secret -`           |
| `atlas config set client.secret -` (rotation)     | `atlas tenants add <name> --tenant-id <id> --client-id <id> --client-secret - --replace` |
| `atlas config get client.id`, `atlas config list` | `atlas tenants list`                                                                     |
| `atlas config unset client.secret`                | `atlas tenants remove <name>`                                                            |
| `atlas config validate` (Graph part)              | `atlas tenants validate [name]`, or `--all`                                              |

`atlas tenants add` takes all three values at once, so a rotation passes the tenant and client IDs again with `--replace`. It checks the formats before writing, then requests a Graph token right away. A failed check keeps the profile and exits `1`.

### Naming the existing profile

`default` works as a name. To give the existing credentials a real one, add them under the new name, make it active, then remove `default`:

```bash
atlas tenants add contoso --tenant-id <tenant-id> --client-id <client-id> --client-secret -
atlas tenants use contoso
atlas tenants remove default
```

`remove` only deletes profiles held in the encrypted store. If `default` comes from top-level fields in `atlas.config.json`, delete those fields from the file instead.

### Several tenants on one host

Add a profile per tenant and select one per run. Scheduled jobs set `ATLAS_PROFILE`, or pass `--profile`, so an interactive `atlas tenants use` on the same account cannot change which tenant and bucket the next scheduled run uses:

```bash
atlas tenants add fabrikam --tenant-id <tenant-id> --client-id <client-id> --client-secret -
atlas --profile fabrikam outlook backup -m john.doe@example.com
```

::: warning Environment variables override every selected profile
A shell or unit that still exports `ATLAS_TENANT_ID`, `ATLAS_CLIENT_ID`, or `ATLAS_CLIENT_SECRET` applies them to whichever profile a command selects. Remove them from systemd units, cron environments, and `.env` files once the credentials live in profiles.

Atlas warns on stderr, naming the variables and the profile, whenever they replace a profile value. When only some are set and they change the tenant ID or client ID, the run is refused with exit code `6`, because it would combine one tenant's ID with another tenant's secret. See [Configuration](/configuration#tenant-profiles).
:::

All profiles share one S3 key and one passphrase, so that key reaches every profile's bucket. When tenants must be isolated at the storage layer, keep a separate installation per tenant. See [Bucket isolation](/operations/storage-layout#bucket-isolation).

## Cross-tenant restore replaces the credential swap

v6 restored into another tenant by exporting the destination's credentials and passing the source tenant with `-t`. That swap still runs, but v7 makes it explicit:

```bash
atlas --profile contoso outlook restore -s <snapshot-id> --target-profile fabrikam -T john.doe@example.com
```

The source profile reads and decrypts the backup, and the target profile writes. The explicit target flag is required. Under a manual swap, v7 keeps the source tenant's identity registry read-only, because Graph answers for the other tenant. See [Cross-tenant restore](/reference/cli-recovery#cross-tenant-restore) and [Graph credentials belong to another tenant](/troubleshooting#graph-credentials-belong-to-another-tenant).

## New workloads and their permissions

Contacts, Calendar, and Teams are opt-in. An app registration granted for v6 keeps backing up Outlook, OneDrive, and SharePoint without changes. Grant these only for the workloads you add:

| Workload | Backup permissions                                                                                                                                                   | Restore                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| Contacts | `Contacts.Read`                                                                                                                                                      | `Contacts.ReadWrite`                    |
| Calendar | `Calendars.Read`                                                                                                                                                     | `Calendars.ReadWrite`                   |
| Teams    | Eight Application permissions, including the protected `ChannelMessage.Read.All`. See [Teams application permissions](/azure-ad-setup#teams-application-permissions) | Export only, through `atlas teams save` |

`ChannelMessage.Read.All` can need Microsoft's approval before Graph returns channel messages, even after admin consent. Request it before you schedule Teams backups.

Replication does not cover the new workloads yet. `atlas replicate` and `atlas rehydrate` refuse contacts, calendar, and Teams snapshot IDs, so a disaster recovery plan built on a replica covers Outlook, OneDrive, and SharePoint only.

## SDK changes

`createAtlasInstance` still takes every setting explicitly and reads no config file, so tenant profiles do not affect SDK hosts. The changes are additions, and the first six can break a TypeScript build:

| Change                                             | Effect on existing code                                                                     |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `AtlasInstance` gains `contacts`, `calendar`, and `teams` | A hand-written object or mock typed as `AtlasInstance` needs all three members |
| `AtlasErrorCode` gains `ATLAS_FORMAT_UNSUPPORTED`  | An exhaustive `switch` over `err.code` needs the new case. The CLI maps it to exit code `9` |
| `AtlasErrorCode` gains `ATLAS_KEY_CONFLICT`        | An exhaustive `switch` over `err.code` needs the new case. Rehydration's refusal to replace a data key carries it, and the CLI maps it to exit code `10` instead of `1` |
| `AtlasErrorCode` gains `ATLAS_WRITE_REFUSED` | An exhaustive `switch` over `err.code` needs the new case. A backup rejects with `RefusedWriteError` when a manifest, index, or cursor it built fails the checks its own reader applies, and stores nothing. Snapshot manifests and indexes are written create-only and read back, so a backup can also reject with `StoredObjectConflictError` or a `StorageError` naming the object. Both are `ATLAS_STORAGE_FAILURE`, and the CLI exits `1` for all three. See [Refused and unconfirmed metadata writes](/troubleshooting#refused-and-unconfirmed-metadata-writes) |
| `AtlasErrorCode` gains `ATLAS_SNAPSHOT_NOT_NEWEST` | An exhaustive `switch` over `err.code` needs the new case. `outlook.deleteSnapshot`, `onedrive.deleteSnapshot`, and `sharepoint.deleteSnapshot`, with their `delete -s` commands, now refuse any snapshot but the newest of the mailbox, owner, or site with `SnapshotNotNewestError`, and the CLI exits `11`. The OneDrive and SharePoint calls now decrypt the manifests to check the order, so they need the tenant's data key |
| `AtlasErrorCode` gains `ATLAS_OWNER_BUSY` | An exhaustive `switch` over `err.code` needs the new case. Every backup, deletion, and quarantine now takes a lease on its mailbox, drive owner, site, or team and rejects with `OwnerBusyError` when another operation holds it. The CLI exits `12`. A host that ran two operations on one owner at once, which was never supported, now gets this error instead of a silently overwritten cursor. See [Concurrent operations](/reference/sdk#concurrent-operations) |
| `checkStorage()` gains `conditionalWrites` | New, always present. The call now writes and removes one probe object under `_meta/storage-check/`, and reports `not_probed` when it may not. A hand-written `StorageCheckResult` mock needs the field |
| Restore options gain `targetTenant`                | A wrapper that copies restore options field by field drops it until updated                 |
| `createTenant`, `AtlasTenant`, `AtlasTenantConfig` | New. See [Cross-tenant restore](/reference/sdk#cross-tenant-restore)                        |
| `teamsPacingShare` on `AtlasInstanceConfig`        | New, optional. Set `1 / n` when `n` processes back up teams of one tenant                   |

## Upgrade steps

Storage is unchanged, so hosts that share a bucket can be upgraded one at a time. Run Contacts, Calendar, and Teams only from v7 hosts. The owner lease only keeps apart hosts that take it, so keep scheduling one operation per mailbox, owner, site, or team until every host is on v7.

1. **Upgrade** `@wisecom/atlas-cli` or `@wisecom/atlas-sdk` to v7.
2. **Check the credentials.** Run `atlas tenants list`. Existing credentials show as `default` and are selected when no other profile is active. Run `atlas tenants validate` and `atlas config validate`.
3. **Update scripts** that call `atlas config set`, `get`, or `unset` on `tenant.id`, `client.id`, or `client.secret`, or that rely on `atlas config validate` to check Graph. Use the table in [What breaks](#what-breaks).
4. **Move per-run credentials into profiles**, if hosts back up several tenants by swapping `ATLAS_*` variables. Add a profile per tenant, set `ATLAS_PROFILE` or `--profile` in each job, and remove the Graph variables from the environment.
5. **Update SDK code** for the TypeScript changes in [SDK changes](#sdk-changes), then run your type checker.
6. **Grant Contacts, Calendar, or Teams permissions** only if you schedule those workloads.
