# Migrating to v6

Atlas 6 changes how Outlook and SharePoint backups are keyed in storage. Neither change is migrated, aliased, or read through a fallback: backups written by v5 are not found by mailbox- or site-scoped commands after the upgrade. Plan the upgrade as a fresh full backup per mailbox and per site.

Atlas 6 also names content objects in every workload by a keyed hash instead of a plain SHA-256. Existing objects stay readable, but the first OneDrive backup after the upgrade stores its content again under the new names.

## What changed

| Workload   | v5 storage key                             | v6 storage key                       |
| ---------- | ------------------------------------------ | ------------------------------------ |
| Outlook    | Lowercased primary SMTP address            | Entra ID object ID of the mailbox    |
| SharePoint | `<hostname>,<site-guid>,<web-guid>`        | `<site-guid>,<web-guid>`             |

The key covers content, manifests, delta cursors, and replication state, so all of them move to the new prefix.

### Outlook: object ID instead of address

Object IDs survive a primary address rename and a conversion to a shared mailbox. A renamed mailbox keeps its prefix, the next run stays incremental, and the catalog shows one mailbox instead of two. OneDrive already keys by object ID, so both workloads now follow the same convention.

`-m` and the SDK `mailboxId` still accept an address. Any value containing `@` is resolved before a storage key is built:

1. As a UPN, with `GET /users/{address}`.
2. On 404, as a primary SMTP address, with `GET /users?$filter=mail eq '{address}'`.

A secondary alias (a proxy address that is neither the UPN nor the primary `mail` value) does not resolve; pass the object ID instead. A value without `@` is used as the object ID directly, with no Graph call. The address is kept only as display metadata on snapshots.

For restore, `-m` or `-s` selects the backup to read and `-T` / `--target` selects the mailbox to write into. `-T` accepts an address or an object ID.

### SharePoint: site ID without the hostname

`--site` still accepts a site URL or a Graph site ID with or without the hostname. Storage now uses only `<site-guid>,<web-guid>`, so a tenant hostname change does not orphan backups. Commands that read existing backups by site ID (`save`, `verify`, `list-snapshots`, `list-versions`, `stats --site`, and the restore source) no longer call Graph, so the backups of a site already deleted from SharePoint stay reachable. `backup` and `--target-site` still resolve through Graph.

### All workloads: keyed content object names

Content objects are named by an HMAC-SHA256 of their plaintext, keyed with a naming key that Atlas derives from the tenant data key (HKDF-SHA256, info `atlas/object-name/v1`). A v5 name was the plain SHA-256 of the plaintext, so anyone with read access to the bucket could hash a known file and check whether an owner stored it, without the passphrase. A v6 name cannot be computed without the data key. Mailbox objects also no longer carry the `x-plaintext-sha256` metadata header. See [What object names reveal](/security#what-object-names-reveal).

Manifests still record the plain SHA-256 inside their encryption, and restore, save, and verify follow each manifest entry to its object, so v5 objects remain readable from v5 snapshots.

## What to expect after upgrading

- **Mailbox- and site-scoped commands** (`-m`, `--site`) find only backups written by v6.
- **Snapshot-scoped commands** still read v5 backups. `atlas outlook list` shows each old address prefix as its own row, with the address in the **Owner ID** column. Pass the old snapshot ID with `-s` and without `-m`, for example `atlas outlook restore -s <snapshot-id> -T user@example.com`. The ID is in the old manifest key, `manifests/{address}/{snapshot-id}.json`.
- **The first backup is full.** Deduplication is per owner prefix, so the new copy is stored in full and storage use roughly doubles until the old prefixes are deleted.
- **The first OneDrive backup re-uploads content.** The prefix is unchanged, but no existing object matches a keyed name, so each owner's content is stored once more. Later runs deduplicate as before.
- **v5 objects keep their plain SHA-256 names** and stay open to the file-confirmation check above until deleted. Deleting a snapshot with `-s` removes only its manifest, so removing them means deleting the owner's backup (`atlas onedrive delete`, or the v5 deletions in step 1) and taking a fresh full backup.
- **Old objects stay in the bucket** until deleted. Object Lock retention blocks deletion until it expires; it never removes objects by itself.

## Replication targets

Replication copies one way and never deletes, so a target keeps every v5 snapshot it received, including those you delete from primary in step 2. Targets need no upgrade of their own: they are buckets, and only the host that runs `atlas replicate` or `atlas rehydrate` is upgraded.

After the upgrade, replicated v5 snapshots follow the same rules as v5 snapshots on primary:

| Command                                                                 | Reaches v5 snapshots |
| ----------------------------------------------------------------------- | -------------------- |
| `atlas replicate -s <snapshot-id>`, `atlas rehydrate -s <snapshot-id>`  | Yes                  |
| `atlas rehydrate --all`                                                 | Yes, every prefix    |
| `atlas replicate` and `atlas rehydrate` with `-m` or `--site`           | No, v6 prefixes only |

`restore`, `save`, and `verify` read primary only. To restore a v5 snapshot held only on a target, copy it back first, then read it by snapshot ID:

```bash
atlas rehydrate -s <snapshot-id> --source-config ./offsite.json
atlas outlook restore -s <snapshot-id> -T user@example.com
```

`rehydrate --all` copies back any v5 snapshot that is missing from primary. After a step 2 deletion, that is every v5 snapshot the target holds, so a disaster recovery drill brings the deleted data back to primary. If you do not want to keep the v5 data, delete it on each target too. The delete commands have no target flags, so run the step 2 commands with v5 pointed at the target, by setting `ATLAS_S3_ENDPOINT`, `ATLAS_S3_ACCESS_KEY`, and `ATLAS_S3_SECRET_KEY` to the target's values for that shell.

Replication between a v5 host and a v6 host is not supported. A v5 host keys mailboxes by address and SharePoint sites with the hostname, so its `-m` and `--site` runs never select v6 snapshots, and the target silently stops receiving new backups.

## Upgrade steps

Every host that runs Atlas against the same bucket, including the one that drives replication, is upgraded in the same window. A host left on v5 keeps writing backups under the v5 prefixes, which v6 `-m` and `--site` commands do not see, and it recreates the prefixes you delete in step 2.

1. **Stop scheduled runs** on every host: cron entries, systemd timers, and any service that calls the SDK on a schedule. Stop replication jobs too. Then wait for running jobs to exit, so none finishes after the upgrade with the old version.

   ```bash
   sudo systemctl disable --now atlas-outlook-backup.timer   # each Atlas timer
   crontab -e                                                # comment out each Atlas line
   ```

   A v5 run between steps 2 and 3 recreates the v5 prefixes. A v6 run before you finish step 4 starts a full backup you did not plan for.

2. **Decide whether to keep the v5 backups.** To remove them, run v5 before upgrading:

   ```bash
   atlas outlook delete -m user@example.com -y                     # one mailbox
   atlas sharepoint delete --site https://contoso.sharepoint.com/sites/finance -y
   atlas delete --purge                                             # whole tenant bucket
   ```

   Objects still under Object Lock retention are reported as retained and the command exits `1`. Keep v5 installed until the delete completes without retained objects, or let retention expire. These commands act on primary only; see [Replication targets](#replication-targets).

3. **Upgrade** `@wisecom/atlas-cli` or `@wisecom/atlas-sdk` to v6 on every host. OneDrive needs no action; its existing snapshots stay usable.

4. **Run a full backup** per mailbox and site:

   ```bash
   atlas outlook backup -m user@example.com --full
   atlas sharepoint backup --site https://contoso.sharepoint.com/sites/finance
   ```

   Passing the object ID to `-m` skips the Graph lookup.

5. **Replicate the new backups**, if you use replication. The first run per mailbox and site copies the whole new prefix, which is about the volume of the full backup:

   ```bash
   atlas replicate -m user@example.com --target-config ./offsite.json
   atlas replicate --site https://contoso.sharepoint.com/sites/finance --target-config ./offsite.json
   ```

6. **Re-enable scheduled runs**, for example `sudo systemctl enable --now atlas-outlook-backup.timer`, and restore the crontab lines. Later runs are incremental.

7. **Update scripts and SDK callers** that build storage paths or compare owner IDs against email addresses. Owner IDs are now object IDs for Outlook and hostname-free site IDs for SharePoint.
